# Ruby GoodJob 4.24 parity and v5 preparation

## Participants

Andrei Makarov (@amkisko)

## Decisions

Track upstream Ruby GoodJob through current 4.x (reference tag `v4.24.1`) and land Elixir progressive enhancements that keep a shared database safe for Ruby v5. Stay on Elixir major `1.x` while new surfaces are additive and dual-path; reserve Elixir `2.0` for removing `concurrency_key`-only APIs when Ruby v5 drops that column.

Ship in three layers:

1. Schema and index parity with Ruby update migrations 16–22 (dequeue-by-queue, executions indexes, batch query indexes, redundant index cleanup, cron index order, `good_job_concurrency_claims` table). Keep `IF NOT EXISTS` / idempotent additive style for shared DBs.
2. Concurrency v5-prep: label-scoped rules as the preferred path; keep key-based checks working with deprecation warnings; implement claims grant/wait/promote against `good_job_concurrency_claims` when the table exists.
3. Runtime defaults that Ruby schedules for v5: `dequeue_query_sort` with `:scheduled_at` as the future-only path (config today, default flip later), `threads` as the canonical name beside `max_threads`, document `:skiplocked` migration path without flipping Elixir's default until Ruby v5 ships (or an explicit Elixir major).

Skip Ruby-only surfaces (ActiveRecord, Fiber isolation, Puma, Stimulus dashboard chrome, Continuation jobs, JRuby) unless they change the shared protocol.

## Effects

All three layers are implemented on `feature/ruby-4-24-and-v5-prep` (uncommitted): schema 16–22, label concurrency + claims, dequeue_query_sort/threads/skiplocked docs. `mix test`: 927 tests, 0 failures. `mix.exs` remains `1.0.1`; CHANGELOG lists Unreleased.
